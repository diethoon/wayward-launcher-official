## Connection and trust flow

1. A future UI scans the JSON QR generated by the Windows Manager and calls `RemoteHostClient.verifyAndStoreQr(context, qrJson)`.
2. The QR's Host Identity signature is verified before the certificate fingerprint is used as a TLS pin. The client then reads `/v1/host/identity` over pinned HTTPS and compares Host ID, public key and certificate fingerprint.
3. The first pairing call submits the Android Keystore P-256 public key. The client verifies the Host-signed challenge, signs the exact payload, and waits for a Windows Manager approval.
4. The approval receipt is checked against the expected Host ID, Pairing ID, Device ID, public-key fingerprint and permission bitmask. A mismatch fails closed.
5. Each subsequent session is acquired with a new Host-signed challenge. The token stays in process memory and expires after 15 minutes.
6. mDNS rediscovery is available only after QR trust. The discovered TXT record must match the saved Host ID/key/certificate fingerprints. The client then connects using the previously saved certificate pin and checks a fresh signed manifest before persisting a new private IPv4 URL.

The mobile client never connects directly to PC port 8188. ComfyUI requests use the authenticated Remote Host gateway only.

## WebView and storage preservation

The official launcher continues using its current `https://localhost:<profilePort>` per-game WebView Origin. No Host URL, bearer token, Device private key, pairing polling secret or ComfyUI credential is passed to game JavaScript. The existing WMLHost bridge is unchanged.

The Native image interceptor sends only the encoded game image path to `/v1/game/images/...` under the previously selected logical root. The PC Host remains responsible for its allow-listed directory boundary, MIME type, ETag, conditional GET and Range handling. Android stores bounded cache files under the app cache directory and validates the exact cache ETag before reusing cached bytes.

The bridge does not change SAF local folder access. When Remote PC mode is not selected, the original SAF/ZIP-mod image path remains the fallback. The existing NovelAI image-generation mode remains separate.

## File operations

- `RemoteFilesClient.list` returns the Host-approved root's logical items.
- `RemoteFilesClient.openDownload` returns a streaming response and requires a valid Host SHA-256 header.
- `beginUpload` returns the Host upload ID and maximum chunk size.
- `appendUploadChunk` uses the exact Host-reported sequential `Upload-Offset` and a maximum 1 MiB chunk.
- `getUploadProgress` queries the authoritative offset after reconnect or process restart.
- `completeUpload` asks the Host to verify final length/hash and atomically place the file.
- `cancelUpload` cancels a session owned by this Device.

The Host decides whether the Device has `BrowseGameLibrary`, `ListFiles`, `DownloadFiles` and `UploadFiles` permissions. Default pairing permissions are read-only.

## ComfyUI and original game ImageGen operations

The current Remote PC mode routes the original game HTML ImageGen API through the existing WebView proxy, then through RemoteGameImageApiClient and the certificate-pinned Host session. The mapped routes are:
- GET /api/image/health and GET /api/pack;
- POST /api/image/generate, GET /api/image/status/{promptId}, POST /api/image/cancel;
- POST /api/image-hit;
- POST /api/batch/enqueue, GET /api/batch/status and POST /api/batch/{pause|resume|clear}.

The bearer token remains inside native Android code. The game JavaScript sees only the original JSON request and response shape. A completed PC output is stored under the selected approved root at __wayward_generated__/img-{promptId}.{ext}; the Host atomically updates __wayward_generated__/pack-index.json and serves the image through the existing authenticated game-resource endpoint. The original game then adds the portrait through its existing image-index path and fetches the same /images/__wayward_generated__/... anchor. Android serves the anchor from the pinned Host through its bounded app-private cache. The per-game HTTPS localhost WebView origin and IndexedDB/localStorage namespace are unchanged.

The separate native Comfy client also supports status, object-info, queue, workflow submission/history/cancel, input uploads and output downloads with SHA-256-verified private caching. The PC Host remains the sole upstream client to 127.0.0.1:8188; Android cannot start or stop ComfyUI.

Current compatibility limitations: the Host uses a built-in ComfyUI graph and the requested or first available installed checkpoint. The original workflow field is a profile label, not a ComfyUI node graph. The request includes loraStrength but no LoRA asset identifier, so this adapter does not apply LoRA strength or custom workflow selection. No model, LoRA, custom node or workflow files are altered. These points require confirmation against the actual user ComfyUI installation.

## Paired-device WAN reconnect — current v2.1 contract

First-time pairing remains LAN-only. The Host QR contains only the private-LAN HTTPS baseUrl, Host ID/public key and the exact TLS certificate SHA-256 pin. The public WAN endpoint is never included in QR JSON or in a pairing manifest. Pairing-manifest retrieval, pairing request, P-256 proof and approval-status endpoints reject clients that are not on the Host's same private LAN subnet. QR issuance itself is Manager-loopback-only.

After the PC user has approved a device and the Host has durably stored its pairing record, Android authenticates with the existing Android Keystore P-256 key. Only after this challenge-response succeeds may the client call authenticated GET /v1/host/connection. The response contains the Host ID, current WAN HTTPS endpoint, exact TLS certificate SHA-256 pin and finite lease expiry. Android verifies the Host ID and pin against the original signed QR before persisting a separate wanBaseUrl field. The signed QR baseUrl and signature are never rewritten.

For normal requests, Android tries the authenticated WAN route, then the most recently verified LAN route, then the original signed QR route. It falls back only for connection-establishment/network errors. TLS/certificate-pin errors, HTTP authentication failures, application responses and request-body write failures never trigger a second route. mDNS discovery updates only the LAN route after the saved TLS pin and Host identity match; it does not request or create a new QR.

The PC Manager owns the router/firewall lifecycle. It creates a finite-lease UPnP IGD mapping for Host TCP 8765 only while the verified Host process is alive (180-second lease, renewed every 60 seconds). The independent worker removes the mapping when Host exits; if the worker/PC loses power, the router's last finite lease must expire. The Manager never forwards ComfyUI 8188 or ImageGen 8189. Android never configures router or Windows Firewall rules.

The current Android CI checks route persistence and validation, but does not prove a real WAN route or physical router behavior. The actual cellular reconnect, new-device WAN pairing rejection, forced Host termination and PC power-off lease expiry must be verified on the real PC/router/handset before release.
